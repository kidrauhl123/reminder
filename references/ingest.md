# 输入从哪来

脑子只有一套：听懂 → 分类 → 写入本地库 → 该叫就叫。信息从哪进来，不改变这套规则。

调度、事项类型、库命令仍以 `SKILL.md` 为准。本文件只回答：有哪些入口、各自授权什么。

Clone 之后，**对话已经够用**。下面后几条是可选能力：接到同一套规则上，不要另发明分类或另一张表。凭证留在使用者自己的机器，不进本仓库。

## 对话（开箱）

用户正在场。随口待办、截图、课表、群通知原文、说「今天/明天有啥事」、说想养成习惯，都走 `SKILL.md` 对话模式。

- 明确说「提醒我」→ 必做
- 丢来带日期或钟点的日程 → 可选场次，不必再问「要不要提醒」
- 说出意愿（早睡、健身）→ 记 intention 并挂一条到点消息
- 探讨拖延/条理/钱/关系、说共勉 → wiki 一起想，默认不收成闹钟

## 群通知 / 课表 / 邮件正文

和用户亲手贴过来的日程同一套处理：有钟点的记 `add-event`，到点轻喊；交材料/报名截止用 `deadline`，提前提醒开始；没有钟点的当背景，不虚构开场时间。

受众和使用者明显不符（例如通知写给另一类学生）时，点明对象，不要当成必做。

## 邮件入站（可选）

本仓库不实现 IMAP，也不收密码。谁要「信一到就处理」，在自己环境里接监听即可：IMAP IDLE、定时拉信、邮箱转发进对话、MCP 都行。

建议分两步，第二步才走模型：

1. **脚本**先发一句：`📧收到新邮件：标题`。不消耗 token，只让用户知道助手已经看到。
2. **再**把 `from` / `subject` / `date` / `body`（及附件名）交给 Agent，按本 skill 读、给人话结论、该进日历的进日历。

不要等用户说「去看邮箱」。营销广告一两句带过。摘要不要贴原文。seen 游标、账号、token 都留在宿主。

## 赛程 / 世界动态（可选）

Happening 是事实层。只有这位用户在乎的过滤结果才进个人日历，规则见 [happening-events.md](happening-events.md)。周报脚本不走模型；关注名单按自己的改。

## 节日

法定假日、农历节日从 [`data/`](../data/) 进本机库，不要手填。学年历、生日只在这位用户自己的 `~/.reminder/`。

## 不要做的

- 为一种入口另发明一套分类或另一张表
- 把监听脚本里的密钥、邮箱地址、会话 token 提交到 git
- 入站信息一律当必做作业
- 没有钟点就编一个开场时间
- 没接邮件/赛程就声称助手不完整
